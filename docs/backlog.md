| Q9 | Macro expansion | Cangjie macros are compiled packages (`lib-macro_<pkg>`, exporting `macroCall_c_<Macro>_<pkg>`, `macroCall_a_…` for attribute macros) run on tokens. R4 with its `LSPMacroServer` leaves an item it could not expand opaque already; on this repository its false errors are on imports from another package of what a macro annotates: `import loupe.{StructureKind, …}` in `cjls` is `'StructureKind' is not accessible in package 'loupe'` (459), `StructureKind` being `@Derive[Equatable] public enum`. Inside its own package it reads as it should, so the name is found and only its `public` lost — likely cjc's `MacroExpandDecl` wrapping the declaration, its modifiers read off the wrapper (not checked). Opaque is not hidden: an item under a macro keeps its written modifiers for every package importing it, and a failed expansion in a package changes nothing another package sees of it. Three layers, after R1, running a macro the last of them. **1. A macro that did not expand makes its item opaque, not wrong**, as R4 does: an attribute macro reads as the identity (`@Derive`, `@DeriveExt`, `@Test` only add), a type it touched may have members and interfaces not seen, so nothing is reported as missing on it, and the last expansion that succeeded stands until a new one does (R1 reports `unresolved-proc-macro` alone). **2. `std`'s macros are expanded by cjls**, as R1 does its builtin derives: `std.deriving`, `std.unittest`, only the declarations they add; no SDK needed. **3. The workspace's macros are run**, out of process: the runtime linked into cjls cannot load a `lib-macro_*` built by the user's cjc, so the process is built with it — R4's `LSPMacroServer` (as R9), or a small server of our own shipped as sources and built once with the user's `cjpm`, cached per `cjc --version`, as R1 takes `proc-macro-srv` from the sysroot (protocol and failures ours). Loading in-process (cjlsp) takes the server down with a crashing macro. Building the macro packages is R1's `cargo check` problem: a slow first start with macros unresolved until it ends, the target directory locked against the user's own builds and artifacts evicted between the two (R1's `cargo.targetDir`), nothing when the workspace does not build; and cjpm leaves `*.cj.macrocall` and `lib-macro_*` in `src/`. So a target directory of our own, and only the macro packages and what they import built. An expansion is a query keyed by the macro and its input tokens, spans mapped back to the input |
